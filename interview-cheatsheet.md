# System Design Interview Cheat Sheet

> **How to use this:** For every component, read the 7-8 lines out loud. That's exactly what you'd say in an interview when asked "Tell me about X." Each definition is packed with specific technical details that signal real depth — internal mechanisms, numbers, trade-offs. If you can say these lines, the interviewer knows you understand the component at a fundamental level.

## 🗄️ Databases

### Redis
Redis is an in-memory key-value store that achieves sub-millisecond latency by keeping all data in RAM and using a single-threaded event loop — which eliminates lock contention and context switching entirely. It's not just key-value though: it supports rich data structures like sorted sets (powering leaderboards via skiplist + hash dual encoding), hashes (ziplist for small, hashtable for large), lists (quicklist = linked list of ziplists), and HyperLogLog for probabilistic counting in fixed 12KB. Persistence is optional via RDB (point-in-time snapshots through fork) or AOF (append-only command log with fsync everysec), and I typically enable both in production — RDB for backups, AOF for durability with max 1 second data loss. For scaling beyond one core, I'd use Redis Cluster which shards data across 16,384 hash slots using CRC16, with automatic MOVED redirections when a key lands on the wrong node. The main pitfalls I watch for are: never run KEYS * in production (blocks the event loop — use SCAN instead), watch for big keys that block on deletion (use UNLINK), and handle cache stampedes with probabilistic early expiration or mutex locks.

### MySQL (InnoDB)
MySQL with InnoDB uses a clustered index architecture — the table data IS the B+ tree, physically ordered by the primary key, which means range scans on PK are sequential disk reads and very fast. This is why auto-increment integer primary keys are ideal — they cause sequential appends at the end of the B+ tree, whereas UUID primary keys cause random inserts and page splits that fragment the index. Secondary indexes store the primary key value (not a row pointer), so a secondary index lookup requires two B+ tree traversals. MVCC is implemented via undo logs — when a transaction modifies a row, the old version is stored in the undo log so that concurrent readers can see a consistent snapshot without blocking writers. Durability is guaranteed by the binary log (binlog) for replication and the InnoDB redo log (ib_logfile) for crash recovery via write-ahead logging. At scale, companies like Facebook and Flipkart shard MySQL by user_id across thousands of instances, each holding about 1 million users, with a custom sharding layer routing queries and cross-shard joins done in application code. For managed sharding, Vitess (used by YouTube) sits between the application and MySQL, transparently routing queries to the correct shard.

### PostgreSQL
PostgreSQL uses a heap-based storage model — unlike MySQL's clustered index, the table data is unordered, and every index (B-tree, GIN, GiST, BRIN) points directly to rows via CTID (page number + slot offset), meaning any index is equally fast with a single lookup. MVCC is implemented differently from MySQL: PostgreSQL stores multiple versions of each row (tuples) with xmin (transaction that created it) and xmax (transaction that deleted it) metadata in the tuple header — readers check these against their transaction snapshot to determine visibility, and dead tuples are cleaned up by autovacuum. This means writes never block reads and vice versa, but it also means PostgreSQL needs VACUUM to reclaim space from dead tuples. Its biggest advantage is extensibility: PostGIS for geospatial queries, pgvector for AI/ML embeddings, TimescaleDB for time-series, and JSONB for indexed document queries — making it a true hybrid relational/document/geospatial/AI database. For connection management, I always put PgBouncer in front — it multiplexes 1,000 client connections down to 20 actual PostgreSQL connections (transaction-level pooling), dramatically reducing memory usage on the database server. Companies like Instagram, Uber, Spotify, and Razorpay run their primary OLTP workloads on PostgreSQL.

### Cassandra
Cassandra is a wide-column NoSQL database designed for massive write throughput and zero downtime — it uses a peer-to-peer architecture with no master node, so any node can accept reads and writes, and there's no failover time when a node dies. Writes are extremely fast because they use an LSM-tree (Log-Structured Merge-tree): the write goes to a commit log (sequential append to disk) and a memtable (in-memory sorted map), then acknowledges immediately — no random disk I/O, no locks, no read-before-write. When the memtable fills up (default 128MB), it's flushed to disk as an immutable SSTable. Reads are more complex — they check the memtable first, then use a bloom filter to skip SSTables that definitely don't contain the key, then a partition summary (sparse index) for binary search, then the partition index for exact offset, then finally read the data — so reads are slower than writes. Compaction merges SSTables in the background, and I choose the strategy based on workload: Size-Tiered for write-heavy (less write amplification), Leveled for read-heavy (fewer SSTables to check), Time-Window for time-series. Consistency is tunable per query — ONE, QUORUM, LOCAL_QUORUM, ALL — and the key insight is that QUORUM reads + QUORUM writes guarantee strong consistency because by the pigeonhole principle, R + W > RF means at least one node overlaps between the read and write groups. The main anti-patterns are: don't use secondary indexes (they're per-node, causing scatter-gather), don't create unbounded partitions (hot partitions), and design the partition key around your query pattern since Cassandra doesn't support joins.

### DynamoDB
DynamoDB is AWS's fully managed NoSQL database that abstracts away all operational overhead — no servers to provision, no sharding to manage, automatic replication across three Availability Zones, and single-digit millisecond latency at any scale from 1 item to 10 trillion. Internally, it hashes the partition key to distribute items across partition nodes, and each partition auto-splits when it exceeds 10GB or 3,000 RCU / 1,000 WCU capacity. I choose between two capacity modes: provisioned (I specify RCU/WCU and get lower cost for predictable traffic) or on-demand (pay per request, ideal for unpredictable spikes like a product launch). Each 4KB read costs 1 RCU (eventually consistent) or 2 RCU (strongly consistent), and each 1KB write costs 1 WCU. For secondary access patterns, I use GSI (Global Secondary Index) when I need to query by a different partition key — it's a separate table with its own capacity, eventually consistent, and can be sparse (only items with the indexed attribute appear). LSI (Local Secondary Index) shares the partition key with the base table, is strongly consistent, but must be created at table creation time. DynamoDB Streams gives me change data capture — every insert/update/delete generates a stream record I can trigger Lambda on, which is perfect for real-time indexing to Elasticsearch or sending notifications. For multi-region active-active, Global Tables replicate across regions with last-writer-wins conflict resolution based on timestamps. The biggest mistake I see people make is using Scan (which reads the entire table) instead of Query (which reads one partition) — Scan on a 100GB table is extremely expensive and slow.

### MongoDB
MongoDB is a document database that stores data as BSON (Binary JSON) — each document can have a different structure, so I can add fields without migrations, which is ideal for rapid prototyping and content management. It supports rich queries on nested fields and arrays, an aggregation pipeline for multi-stage data transformation (like SQL GROUP BY with map-reduce semantics), and built-in horizontal sharding where the mongos router distributes writes based on a shard key. Replication uses a replica set — one primary (accepts writes) and multiple secondaries (accept reads), with automatic election of a new primary if the current one dies (typically 10-12 second failover). The main trade-off is that it doesn't support joins — I denormalize by embedding related data within documents or maintaining separate lookup collections. For schema design, the key decision is embedding vs referencing: embed when data is accessed together and is bounded (a blog post with comments), reference when the related data is large or shared across many parents (users referenced in orders). Companies like Uber (early trip data), eBay (catalog), and Adobe (CMS) use MongoDB for its flexibility. The biggest pitfall is unbounded array growth in embedded documents — if a document exceeds 16MB, it errors out, so I use referencing for unbounded relationships.

### Elasticsearch
Elasticsearch is a distributed full-text search engine built on Apache Lucene — instead of scanning every document (like SQL LIKE), it builds an inverted index that maps each term to the list of documents containing it, enabling O(1) lookup for search queries. During indexing, text passes through an analysis chain: character filters (HTML strip) → tokenizer (split into terms) → token filters (lowercase, stop words, stemming, synonyms). So "Running Shoes" becomes ["run", "shoe"] — and searching "running" matches because both query and document are analyzed the same way. Relevance is scored using BM25 — an improvement over TF-IDF that adds saturation: the 10th occurrence of a term contributes less score than the 1st, and it normalizes for document length so short documents with the term rank higher. Each Elasticsearch index is split into shards, and each shard is an independent Lucene instance with its own inverted index stored in immutable segments — new documents go to an in-memory buffer that's refreshed (default every 1 second) into a new segment. I differentiate between text fields (analyzed, for full-text search) and keyword fields (not analyzed, for exact match/filtering/sorting/aggregations) — this is the most common mistake people make. For filtering, I always use the filter context instead of must — filters skip relevance scoring and are cached, making repeated filters essentially free. For deep pagination, I use search_after instead of from + size, because from=10000 forces each shard to return 10010 results to the coordinating node — enormously wasteful.

### Amazon S3
S3 is an object storage service that provides essentially infinite capacity with 99.999999999% (11 nines) durability — achieved by storing each object across multiple disks in three Availability Zones (6+ copies), with continuous background scrubbing that detects and repairs silent data corruption (bit rot), and checksums verified on every read. It's a flat key-value store: the bucket name + key (e.g., "images/users/1001/photo.jpg") uniquely identifies an object, and there are no real folders — the slashes are just visual prefixes. I choose storage classes based on access patterns: Standard ($0.023/GB) for active data, Standard-IA ($0.0125/GB) for infrequent-but-instant access, Glacier Flexible ($0.0036/GB, 1-5 min retrieval) for archives, and Glacier Deep Archive ($0.00099/GB, 12-hour retrieval) for long-term retention — and I automate transitions with lifecycle policies. For large file uploads, I use multipart upload — splitting the file into parts that upload in parallel, with retry only on failed parts, and it's required for files over 5GB. For client-direct uploads (bypassing my server), I generate presigned URLs that grant time-limited access (e.g., 1 hour) without sharing AWS credentials. Since December 2020, S3 provides strong read-after-write consistency for all operations including overwrites and deletes — no more eventual consistency. For event-driven architectures, S3 event notifications can trigger Lambda, SQS, or SNS when objects are created or deleted — perfect for auto-generating thumbnails or transcoding videos.

### Google Bigtable
Bigtable is Google's petabyte-scale wide-column database, designed for massive read/write throughput (millions of ops/sec) with single-digit millisecond latency. It uses a similar data model to Cassandra (row key, column families, columns) but is fully managed on GCP with Google's Colossus filesystem for storage. Internally, data is split into tablets (contiguous row key ranges), each served by a tablet server, with a master balancing tablets across servers. It's optimized for time-series, IoT telemetry, and as a backing store for Google's own products (Search index, Maps, YouTube analytics). The key design decision is the row key — since data is sorted by row key and range scans are the primary access pattern, I design the key to match query patterns (e.g., reverse-timestamp for "latest first" or userid+timestamp for per-user time-series). Unlike Cassandra, Bigtable provides strong consistency per row (not tunable) and supports only single-row transactions. It's a GCP-native service, so I'd only choose it if I'm already on Google Cloud and need massive throughput that exceeds what Cloud Bigtable's competitors offer.

### Google Spanner
Spanner is Google's globally distributed relational database that provides ACID transactions across continents — something that's normally impossible because the speed of light makes synchronous cross-region coordination too slow. Spanner solves this using TrueTime — GPS receivers and atomic clocks in every Google data center that provide a globally consistent time reference with bounded uncertainty (~7ms). This allows Spanner to assign globally meaningful commit timestamps and use Paxos consensus across regions to achieve external consistency (the strongest isolation level — stronger than serializable). It's a SQL database with auto-sharding (splits tables into splits automatically as they grow), multi-region synchronous replication, and 99.999% availability (survives an entire region failing). I'd use it when global ACID is non-negotiable — financial systems spanning continents, ad-tech real-time bidding, global inventory management. The trade-off is write latency: a global transaction takes ~100-200ms (speed of light between regions), and cost is significantly higher than regional databases. Companies like Google (AdWords, Play) run mission-critical workloads on Spanner.

### ClickHouse
ClickHouse is a columnar analytics database that's 100x faster than traditional row-oriented databases for analytical queries — because it stores data column-by-column instead of row-by-row. If I query "average age of 10 million users," a row-oriented DB (PostgreSQL) reads all columns of all rows from disk. ClickHouse reads only the "age" column — 1/4th the I/O for a 4-column table. It uses vectorized execution (processes batches of values in tight CPU-cache-friendly loops), aggressive compression (columnar data compresses 5-10x because similar values are adjacent), and can scan billions of rows in seconds. It's ideal for real-time analytics dashboards, log/event analysis, and user behavior analytics. The trade-off is that it's terrible for OLTP — point lookups (reading a single row by ID) are slow, and updates/deletes are expensive (require rewriting entire partitions). Companies like Uber (trip analytics), Cloudflare (DNS query analytics on billions of rows), and Spotify (listening analytics) use ClickHouse for real-time dashboards.

### Neo4j
Neo4j is a graph database that stores data as nodes (entities) and edges (relationships) — optimized for traversing connections, which is painfully slow in relational databases due to expensive JOINs. A "friends-of-friends-of-friends" query that requires 6 JOINs in SQL (exponentially slow) is a single pattern match in Cypher (Neo4j's query language): `MATCH (a)-[:FRIEND*3]->(friend)` — traversing the graph directly in milliseconds. Internally, Neo4j uses an adjacency list — each node stores pointers to its connected nodes, so traversing an edge is a pointer dereference (O(1)) rather than a B-tree lookup and join. I'd use Neo4j for social graphs (friend recommendations), fraud detection (finding connection patterns between suspicious accounts), recommendation engines (people who bought X also bought Y because of shared graph paths), and network/infrastructure topology. The limitation is write throughput — graph writes require updating adjacency lists with locks, making it slower for high-volume writes compared to Cassandra or DynamoDB.

## 📨 Messaging & Streaming

### Apache Kafka
Kafka is a distributed append-only log, not a traditional queue — messages are persisted for days/weeks and can be re-read by multiple independent consumers, which is fundamentally different from RabbitMQ where messages are deleted after consumption. A topic is split into partitions (ordered, append-only sequences), and the partition is the unit of parallelism — each partition has one leader (handles all reads/writes) and ISR followers that replicate, with ZooKeeper or KRaft managing leader election. The key design choice is the partition key: hash(key) % num_partitions determines the partition, so all events for a specific user_id always land on the same partition in order — which is critical for ordered processing. Consumers organize into consumer groups where each partition is read by exactly one consumer in the group, and the consumer controls its position (offset) — it can rewind, replay, or reprocess historical events. For durability, I use acks=all with min.insync.replicas=2 and replication factor=3 — meaning the leader and at least one replica must confirm before acknowledging. Kafka achieves massive throughput (millions/sec per cluster) through sequential disk I/O, Linux page cache (bypassing JVM heap), zero-copy sends (disk → network, no CPU copy), and producer batching (accumulate events for 20ms or 16KB before sending). For exactly-once semantics, Kafka transactions combine an idempotent producer (PID + sequence number deduplication) with transactional consumer reads — atomic across topics. Companies like LinkedIn (created it, 7 trillion msgs/day), Netflix (700B events/day), and Uber (driver GPS) run their entire event infrastructure on Kafka.

### RabbitMQ
RabbitMQ is a traditional message broker built on AMQP — it excels at flexible message routing, not event streaming. The core model is exchanges → queues: producers publish to an exchange, and routing rules (bindings) determine which queue(s) receive the message. I choose exchange types based on routing needs: direct (exact match on routing key), topic (pattern match like "orders.*.created"), fanout (broadcast to all queues), or headers (match on message attributes). Messages are deleted after a consumer acknowledges them — there's no replay like Kafka. RabbitMQ supports priority queues, dead-letter exchanges (failed messages go to a DLQ for inspection), and TTL on messages and queues. It's ideal for task distribution ( distributing work across N workers), request-reply patterns (RPC over messaging), and complex routing topologies. The trade-off vs Kafka is throughput (RabbitMQ handles ~50K msgs/sec vs Kafka's millions) and no event retention/replay. I'd choose RabbitMQ when I need flexible routing and point-to-point delivery, and Kafka when I need event streaming, replay, and high throughput.

### Amazon SQS
SQS is AWS's fully managed message queue — fully serverless, no brokers to manage, infinite scaling, pay-per-request pricing. It comes in two flavors: Standard (at-least-once delivery, no ordering guarantee, nearly unlimited throughput) and FIFO (exactly-once processing, strict ordering, but capped at 300 messages/sec). The key mechanism is visibility timeout — when a consumer receives a message, it becomes invisible to other consumers for N seconds; if the consumer processes and deletes it within that window, great, otherwise it becomes visible again for retry. Dead-letter queues capture messages that fail after N delivery attempts, preventing poison pills from blocking the queue. SQS is perfect for decoupling services in AWS — order service pushes to SQS, worker services pull and process independently, smoothing traffic spikes. The main limitation vs Kafka is no replay (messages deleted after consumption) and no streaming/multiple independent consumers reading the same events.

### Redis Streams
Redis Streams is Redis's built-in append-only log — like a mini-Kafka inside Redis. It supports consumer groups (multiple workers dividing events), message IDs with timestamps (like Kafka offsets), a pending entries list for unacked messages (if a consumer crashes, another can claim its pending messages via XCLAIM), and blocking reads (XREAD BLOCK). The advantage over Kafka is simplicity and latency — it's already in your Redis instance, sub-millisecond operations, no separate cluster to manage. The limitation is throughput (~100K events/sec vs Kafka's millions) and scale — Redis Streams live in RAM, so the log size is bounded by available memory. I'd use Redis Streams for lightweight event streaming within a single service or when I already have Redis and don't want to introduce Kafka.

## 🌐 Networking & Protocols

### WebSocket
WebSocket provides a persistent, full-duplex TCP connection between client and server — both sides can send messages at any time with near-zero latency (~2-14 bytes per frame vs ~800 bytes per HTTP request). It starts as an HTTP GET with an Upgrade header, the server responds with 101 Switching Protocols (computing Sec-WebSocket-Accept by SHA-1 hashing the client's key + a magic GUID), and then the connection switches from HTTP to the WebSocket protocol. Data is sent in frames with opcodes (0x1 text, 0x2 binary, 0x8 close, 0x9 ping, 0xA pong), and client-to-server frames must be masked (XOR with a random key) to prevent cache poisoning of intermediary proxies. I always implement heartbeats (ping/pong every 25-30 seconds) because NAT timeouts, mobile network switches, and proxy idle timeouts silently kill connections — without heartbeats, the server holds dead connections indefinitely. The hardest scaling challenge is that connections are stateful — User A on Server 3 can't directly reach User B on Server 7, so I use a Redis Pub/Sub message bus where each server subscribes to channels for its connected users and other servers publish messages through Redis. At scale (WhatsApp 2B connections, Discord 150M), each connection server holds 50,000-100,000 connections (limited by RAM at ~20-50KB per connection), and I run hundreds of servers behind a Layer 7 load balancer.

### Server-Sent Events (SSE)
SSE is a one-way streaming protocol (server → client only) built on standard HTTP — the server keeps the response open and pushes events using the text/event-stream content type, and the browser's EventSource API automatically reconnects if the connection drops. It's simpler than WebSocket because it's just HTTP — no protocol upgrade, no custom framing, works through all proxies. The main limitation is it's one-directional (server can push but client can't send back) and browsers limit to 6 concurrent SSE connections per domain over HTTP/1.1 (HTTP/2 removes this limit). I choose SSE over WebSocket when I only need server-to-client push (live score updates, notifications, social feed pushes) — it's simpler, auto-reconnecting, and doesn't require a custom protocol.

### gRPC
gRPC is Google's high-performance RPC framework that's 5-10x faster than REST+JSON — it uses Protocol Buffers (binary serialization with field numbers instead of field names, so "user_id" becomes 1 byte instead of 10), HTTP/2 (multiplexing thousands of concurrent RPCs on a single TCP connection with HPACK header compression that sends only header deltas after the first request), and compiled type-safe stubs generated from .proto files. It supports four RPC types: unary (request-response, like REST), server streaming (live updates), client streaming (batch uploads), and bidirectional streaming (chat). The .proto schema provides backward/forward compatibility — I can add new fields without breaking old clients (they ignore unknown fields), but I must never change field numbers or types. For microservice communication, I always set deadlines that propagate through the call chain — if a client gives 2 seconds, the server passes the remaining time to downstream services, and if the deadline expires, the entire call tree is cancelled. The main challenge is load balancing — HTTP/2's long-lived connections defeat traditional L4 load balancers (all traffic goes to one server), so I use client-side load balancing (gRPC client knows all backends and round-robins) or Envoy proxy sidecars.

### WebRTC
WebRTC is a peer-to-peer protocol for real-time audio/video/data in browsers — it bypasses servers for the actual media stream, sending data directly between participants' devices over UDP. The connection setup is complex: signaling (exchanging SDP offers/answers via WebSocket), ICE candidate gathering (finding each peer's public IP via STUN servers), and NAT traversal (if direct P2P fails, traffic relays through TURN servers). For video conferencing beyond ~4 participants, P2P mesh becomes impractical (each participant sends to all others = N² connections), so I use an SFU (Selective Forwarding Unit) architecture — each participant sends one stream to the server, and the server forwards the appropriate streams to each participant (scales to hundreds). WebRTC uses simulcast — the client sends multiple resolutions (1080p, 720p, 360p) simultaneously, and the SFU forwards the appropriate quality to each receiver based on their bandwidth. This is how Zoom, Google Meet, and Discord handle video calls.

### MQTT
MQTT is a lightweight pub/sub protocol designed for IoT devices with constrained bandwidth — the header is just 2 bytes, and it uses a broker-based topic hierarchy (e.g., "home/livingroom/temperature"). It supports three QoS levels: 0 (at-most-once, fire and forget), 1 (at-least-once, with acknowledgment and possible duplicates), and 2 (exactly-once, with four-step handshake). Retained messages keep the last value on a topic so new subscribers immediately get the current state. The Last Will and Testament (LWT) feature lets the broker auto-publish a message if a client disconnects unexpectedly — perfect for presence/online status. Paytm's soundbox uses MQTT to receive payment confirmations — the device subscribes to its payment topic, and when a transaction completes, the server publishes to that topic, triggering the audio announcement.

### HTTP/2
HTTP/2 is a binary protocol (not text like HTTP/1.1) that enables multiplexing — thousands of concurrent requests on a single TCP connection, eliminating the HTTP/1.1 bottleneck of one-request-per-connection. It uses HPACK for header compression (maintains a static and dynamic table of common headers, sends only the difference from previous requests). Stream priorities let the client tell the server which responses are most important (e.g., CSS before images). Server push (deprecated but historically important) allowed the server to proactively send resources it knew the client would need. HTTP/2 is the foundation for gRPC and is what makes modern web performance possible — SPDY (Google's experimental protocol) evolved into the HTTP/2 standard in 2015.

## ⚖️ Infrastructure & DevOps

### Nginx
Nginx is a web server and reverse proxy that uses an event-driven, asynchronous architecture — unlike Apache's thread-per-connection model (which uses ~2MB of memory per thread), Nginx uses a single worker process per CPU core with an epoll-based event loop that can handle 10,000+ concurrent connections per worker. As a load balancer, it distributes traffic across backend servers using round-robin, least connections, or IP hash algorithms, with active health checks that remove failed servers from the pool. I configure it with upstream blocks defining backend pools, location blocks for URL-based routing (/api/ → API servers, /static/ → CDN), and rate limiting zones (limit_req) to prevent abuse. For SSL/TLS termination, Nginx handles the decryption so backend servers don't need to deal with certificates — this offloads CPU-intensive TLS work. It's also excellent as a content cache (proxy_cache) and for serving static files directly (sendfile + tcp_nopush for zero-copy file serving).

### HAProxy
HAProxy is a dedicated Layer 4/TCP and Layer 7/HTTP load balancer known for rock-solid reliability — it's been the load balancer of choice for high-traffic sites like Stack Overflow and Reddit. It provides detailed health checks (TCP check, HTTP check, custom scripts), connection draining during deploys (stop sending new connections but let existing ones finish), sticky sessions via cookies or tables, and extremely detailed statistics (the /haproxy?stats endpoint shows real-time connection counts, response times, and error rates per backend). For Layer 4, HAProxy operates on raw TCP — it doesn't inspect HTTP content, making it faster but less intelligent. For Layer 7, it can route based on URL paths, headers, or cookies. I typically use HAProxy when I need precise control over load balancing behavior and connection management — especially for database load balancing (it can distribute reads across PostgreSQL replicas).

### Envoy
Envoy is a modern Layer 7 proxy designed for microservice architectures — it's the backbone of service meshes like Istio. Unlike Nginx (configuration via static files), Envoy is dynamically configured via APIs (xDS protocol), meaning routing rules, health checks, and load balancing policies update without restarts. As a sidecar proxy (one Envoy container next to each service container), it handles all inbound and outbound traffic — providing mTLS encryption between services, circuit breaking (stop sending to failing services), retries with budgets, distributed tracing (automatically injecting trace headers), and traffic mirroring (shadow traffic to a new version for testing without affecting production). Envoy supports gRPC natively (understands HTTP/2 frames), making it ideal for gRPC load balancing where traditional L4 load balancers fail due to long-lived HTTP/2 connections. Companies like Lyft (created Envoy), Twitter, and Salesforce use it extensively.

### Kubernetes
Kubernetes is a container orchestration platform that automates deployment, scaling, and management of containerized applications — I describe the desired state (3 replicas of my app) in YAML, and Kubernetes continuously reconciles the actual state to match it through controller loops. The control plane (API server, etcd, scheduler, controller manager) manages the cluster, while worker nodes run the actual pods. A Pod is the smallest unit — not a container, but a group of containers sharing the same network namespace and volumes (the sidecar pattern: main app + log forwarder + service mesh proxy in one pod). For stateless apps I use Deployments (with rolling updates and rollbacks); for stateful apps like databases I use StatefulSets (stable pod names web-0, web-1, persistent volumes per pod, ordered startup/shutdown); for node-level daemons I use DaemonSets (log collectors, monitoring agents on every node). Services provide stable networking — ClusterIP for internal, LoadBalancer for external, Ingress for HTTP routing. Auto-scaling is layered: HPA scales pod count based on CPU/memory metrics, Cluster Autoscaler adds/removes nodes when pods can't be scheduled. The key insight is that Kubernetes replaces manual operations with declarative configuration and self-healing — if a pod dies, the ReplicaSet controller starts a replacement within seconds without human intervention.

### Docker
Docker is a containerization platform that packages an application with all its dependencies (libraries, runtime, configuration) into a single portable image — solving the "works on my machine" problem. Unlike VMs which virtualize the entire OS (each VM runs a full kernel, ~2GB overhead), Docker containers share the host OS kernel and use Linux namespaces (PID, network, mount, UTS, IPC) for isolation and cgroups for resource limits (CPU, memory, I/O). A container starts in milliseconds (just a process) vs minutes for a VM (boot an OS). Images are built in layers — each Dockerfile instruction creates a read-only layer, and Docker caches layers so rebuilds are fast (only changed layers rebuild). In production, I always pin specific image versions (not :latest), use multi-stage builds to keep images small (compile in one image, copy binary to a minimal runtime image), run containers as non-root users, and set resource limits (CPU/memory) to prevent noisy neighbors.

### Cloudflare / CDN
A CDN (Content Delivery Network) places servers (edge nodes) in hundreds of cities worldwide so users fetch content from a server physically near them — reducing latency from cross-continent (~150ms) to local (~5ms). When a user requests a cached object, the nearest edge node serves it directly; on a cache miss, the edge fetches from the origin server, caches it (with a TTL), and serves future requests from cache. Cloudflare operates ~330 city-level PoPs with a free tier that includes DDoS protection, SSL/TLS termination, and a WAF (Web Application Firewall) — making it the easiest CDN to start with. For video streaming, Netflix built their own CDN (Open Connect) — placing cache appliances inside ISP data centers so video traffic never crosses the public internet. Akamai has ~4,200 edge locations (the largest physical footprint) and is used by enterprises and Apple/Microsoft. CloudFront is AWS's CDN with ~600 PoPs, tightly integrated with S3 and Lambda@Edge (run JavaScript at edge locations for personalization, A/B testing, auth checks without hitting origin).

## ⚙️ Data Processing

### Apache Spark
Spark is a distributed data processing engine that's up to 100x faster than Hadoop MapReduce — because it performs in-memory computation (caches intermediate results in RAM across the cluster) instead of writing every intermediate step to disk. It uses resilient distributed datasets (RDDs) — immutable, partitioned collections that track their lineage (how they were derived), so if a partition is lost, Spark can recompute it from the lineage graph. I write transformations (map, filter, join, groupBy) that build a DAG (directed acyclic graph) of operations, and actions (collect, count, save) that trigger actual execution — Spark's Catalyst optimizer rearranges the DAG for efficiency before running anything. For structured data, I use DataFrames/Datasets with a SQL-like API. Spark is batch-oriented (micro-batch for streaming via Spark Streaming) — for true real-time streaming with millisecond latency, I'd use Flink instead. I'd use Spark for large-scale ETL (extract-transform-load), machine learning model training (MLlib), and interactive analytics on petabyte-scale data.

### Apache Flink
Flink is a true stream processing engine (not micro-batch like Spark Streaming) — it processes events one-at-a-time with sub-millisecond latency, enabling real-time fraud detection, anomaly detection, and live dashboards. It provides exactly-once semantics through a checkpointing mechanism — periodically snapshoting the application state (using a variant of the Chandy-Lamport distributed snapshot algorithm) so that if a failure occurs, the system can restart from the last consistent checkpoint without duplicates or data loss. Flink supports event-time processing (handling out-of-order events using watermarks), stateful computations (maintaining per-key state like running totals or session windows), and windowing (tumbling, sliding, session windows). I'd use Flink when I need real-time event processing with strong consistency guarantees — Uber uses it for surge pricing (processing driver location streams), Netflix for real-time alerting, and financial institutions for fraud detection on transaction streams.

### Apache Airflow
Airflow is a workflow orchestration tool — I define data pipelines as directed acyclic graphs (DAGs) in Python, where each node is a task (run a SQL query, train a model, send an email) and edges define dependencies (task B runs after task A completes). The scheduler continuously monitors DAGs and triggers tasks based on their schedule (cron expressions) and dependencies, distributing execution across worker nodes. Key features include retries with exponential backoff, SLA monitoring (alert if a task is late), XComs (pass small data between tasks), and a rich UI for monitoring pipeline status, viewing logs, and manually triggering/rerunning tasks. I use Airflow to orchestrate ETL pipelines (extract from APIs → transform in Spark → load to warehouse), ML pipelines (retrain models daily), and data quality checks. Companies like Airbnb (created Airflow), Spotify, and Robinhood orchestrate their entire data infrastructure with it.

## 📊 Monitoring & Observability

### Prometheus
Prometheus is a metrics collection and alerting system based on a pull model — it actively scrapes metrics from instrumented services at regular intervals (every 15-60 seconds) via HTTP /metrics endpoints, rather than services pushing metrics to it. Metrics are identified by name and labels (multi-dimensional: `http_requests_total{method="GET", status="200", endpoint="/api/users"}`), and Prometheus stores them in a time-series database optimized for range queries and aggregations. I write alerts in PromQL (Prometheus Query Language) — e.g., `rate(http_requests_total{status="500"}[5m]) > 10` triggers when error rate exceeds 10/sec. The key design principle is that Prometheus is for metrics (numeric time-series: CPU usage, request count, latency percentiles), NOT for logs (text events) or traces (request paths across services). For high availability, I run two Prometheus instances (both scrape the same targets) and use Alertmanager for deduplication and routing of alerts.

### Grafana
Grafana is a visualization and dashboarding tool that queries multiple data sources (Prometheus, Elasticsearch, InfluxDB, CloudWatch, PostgreSQL) and renders time-series graphs, heatmaps, gauges, and tables. I build dashboards with templating variables (select environment, service, time range from dropdowns), set thresholds on panels (green/yellow/red based on latency or error rate), and configure alert rules that notify via Slack, PagerDuty, or email when metrics cross thresholds. Grafana is the standard visualization layer in the Prometheus + Grafana stack — Prometheus collects and stores metrics, Grafana visualizes them. It's used by virtually every company running Kubernetes (the default K8s monitoring stack includes Grafana).

### Jaeger / Distributed Tracing
Jaeger (pronounced "yay-ger") is a distributed tracing tool — when a request traverses multiple microservices, tracing assigns a unique trace ID that propagates through every service via headers, and each service records spans (start time, end time, operation name) for its portion of the work. The result is a visual timeline showing exactly where time was spent: "Gateway: 5ms → Auth Service: 2ms → Order Service: 45ms → Inventory: 30ms → Database: 28ms." This is invaluable for debugging latency in microservices — without tracing, a slow request is a mystery (which of 10 services is slow?). Jaeger (created by Uber, now CNCF) and Zipkin (created by Twitter) are the two main open-source options, both implementing the OpenTelemetry standard. I instrument services with OpenTelemetry SDKs that automatically trace HTTP/gRPC calls, database queries, and message queue operations — giving me end-to-end visibility across the entire request path.

## 🔤 Languages & Runtimes (Why Companies Chose Them)

### Erlang
Erlang was built by Ericsson for telecom switches in the 1980s — designed for massive concurrency (millions of lightweight processes, each ~2KB vs 2MB for an OS thread), fault tolerance (let it crash philosophy — supervisors restart failed processes), and hot code swapping (upgrade systems without downtime). WhatsApp chose Erlang because their workload (messaging) maps perfectly to Erlang's actor model: each user connection is an independent Erlang process that can send/receive messages, and if one process crashes, it doesn't affect any other. WhatsApp ran 2 billion connections on ~1,000 Erlang servers. Discord originally used Erlang too (before moving to Go for better tooling and performance at their specific scale).

### Go
Go (Golang) was created by Google to solve the problem of building scalable, concurrent server software with fast compilation and simple deployment. Go's goroutines are lightweight threads (~2KB stack, managed by Go runtime, not the OS) — you can spawn 100,000+ goroutines easily, making concurrent HTTP servers trivial. Go compiles to a single static binary (no JVM, no runtime dependencies), making Docker images tiny and deployments clean. Discord moved from Erlang to Go because Go's tooling, performance profiling, and developer ecosystem were better suited for their team. Uber, Twitch, and Dropbox use Go for high-performance microservices where latency matters.

### Memcached
Memcached is a simpler alternative to Redis — it's a pure, multi-threaded key-value cache with no data structures, no persistence, and no replication. It does exactly one thing: store key-value pairs in RAM for fast retrieval. Because it's multi-threaded (unlike Redis's single thread), it can utilize all CPU cores on a machine out of the box. Each value can have its own expiration time (TTL), and evictions use true LRU (Least Recently Used). It uses a slab allocator that divides memory into fixed-size chunks to avoid fragmentation — a 1KB item goes into a 1KB slab, a 4KB item into a 4KB slab. Facebook runs thousands of Memcached instances (they built their own optimizations like mcrouter for sharding), and YouTube was originally powered by Memcached. I'd choose Memcached over Redis when I need pure, multi-threaded, simple caching with no bells and whistles, and the absolute lowest overhead. For anything needing data structures, persistence, or pub/sub, Redis is the better choice.

### Protocol Buffers (Protobuf)
Protobuf is Google's binary serialization format that's 3-10x smaller and 10-100x faster to serialize/deserialize than JSON — because it uses field numbers (1 byte) instead of field names ("user_id" = 10 bytes), varint encoding (small numbers use fewer bytes), and is binary (no braces, quotes, colons, whitespace). The schema is defined in a .proto file (syntax = "proto3"), and the protoc compiler generates type-safe classes for Go, Python, Java, C++, JavaScript — so client and server share a contract at compile time, catching field mismatches before runtime. Schema evolution is built in: I can add new fields (old clients ignore unknown field numbers), remove fields (mark as reserved to prevent reuse), but never change field numbers or types. This is critical for microservices with independent deployment cycles. Companies like Google (created it), Netflix, and Uber use Protobuf for all internal gRPC communication.

### GraphQL
GraphQL is a query language for APIs that solves REST's over-fetching (downloading 50 fields when you need 3) and under-fetching (making 5 API calls to render one screen) problems — the client sends a single query specifying exactly which fields it wants, and the server returns a response with only those fields. It uses a strongly-typed schema (type definitions with fields, arguments, and relationships), and the server resolves each field via resolver functions that can call different backend services. For example, `query { user(id:1) { name orders(last:5) { total } } }` fetches the user's name and last 5 order totals in one request — REST would need 2 calls. Mutations handle writes (create/update/delete with a response), and subscriptions enable real-time updates over WebSocket. The trade-off is complexity (server-side resolver implementation, N+1 query problem solved via DataLoader batching), harder HTTP caching (single POST endpoint vs REST's URL-based caching), and performance monitoring (arbitrary-depth queries can be expensive). Facebook created GraphQL for their mobile app, and GitHub, Airbnb, Netflix, and Pinterest use it heavily.

### Apache ZooKeeper
ZooKeeper is a distributed coordination service that provides configuration management, distributed locking, leader election, and service registry — it's the "coordination kernel" that distributed systems like Kafka (pre-KRaft), HBase, and Solr use to agree on cluster state. Internally, it's a replicated hierarchical key-value store (like a filesystem: /app/config, /app/leaders/node-1) with strong consistency via ZAB (ZooKeeper Atomic Broadcast, a Paxos variant). An ensemble of 3 or 5 servers provides quorum — writes go through the leader and are replicated to all nodes; reads can be served by any node (potentially slightly stale). Watches allow clients to get notified when a znode changes (e.g., "tell me when the leader changes"). Kafka traditionally used ZooKeeper for broker metadata and leader election, but is replacing it with KRaft (built-in Raft) starting in Kafka 2.8 to simplify deployment and improve scalability. I'd use ZooKeeper when building a distributed system that needs coordination primitives — but etcd is a more modern alternative.

### etcd
etcd is a distributed key-value store created by the CoreOS team (now CNCF) — it's the backbone of Kubernetes, storing all cluster state (pods, services, configurations, secrets). It uses Raft consensus for strong consistency: writes go through the leader, are replicated to a quorum of nodes, and are only committed after majority acknowledgment. A cluster of 3 or 5 etcd nodes provides fault tolerance (survives 1 or 2 failures respectively). Unlike ZooKeeper (which uses a hierarchical filesystem-like model), etcd uses a flat key-value model with lease-based TTLs. Reads are linearizable (strongly consistent) by default. The most critical operational fact: if etcd is lost, the Kubernetes cluster state is gone — so I always back up etcd with periodic snapshots (etcdctl snapshot save). etcd is lighter, simpler, and more modern than ZooKeeper, making it the preferred choice for new distributed systems.

### Apache Pulsar
Pulsar is a pub/sub messaging system created by Yahoo that separates compute (brokers) from storage (BookKeepers/Bookies) — unlike Kafka where brokers store data directly on disk, Pulsar brokers are stateless and route reads/writes to Apache BookKeeper storage nodes. This separation allows independent scaling of throughput (add more brokers) and storage capacity (add more bookies). Pulsar supports multi-tenancy natively (multiple teams share one cluster with isolated namespaces), geo-replication built-in (cross-region replication without external tools), and tiered storage (old segments auto-move to S3). It supports both queueing (shared subscriptions) and streaming (exclusive/failover subscriptions). The trade-off vs Kafka is higher operational complexity (two systems: brokers + bookies) and a smaller ecosystem. I'd choose Pulsar when I need multi-tenancy, compute-storage separation, or native geo-replication — Twitter, Yahoo, and Tencent use it at scale.

### Amazon Kinesis
Kinesis is AWS's managed alternative to Kafka — fully serverless, no brokers to provision, auto-scales based on shard count. Kinesis Data Streams uses shards (each shard handles 1MB/sec input and 2MB/sec output), and I provision the right shard count based on throughput needs. Producers use the KPL (Kinesis Producer Library) for batching and retries, and consumers use KCL (Kinesis Client Library) which manages shard assignment and checkpointing across worker instances. Records are ordered within a shard (partition key → shard via hash), and retained for 24 hours to 365 days. The trade-off vs Kafka is lower throughput per shard (1MB/sec vs Kafka's partition-level millions), AWS lock-in, and per-shard pricing that gets expensive at high scale. I'd choose Kinesis when I'm already on AWS and want managed streaming without operating Kafka — but Kafka (especially MSK, managed Kafka on AWS) is usually more cost-effective and flexible.

### Vitess
Vitess is a database clustering layer for MySQL that makes it horizontally scalable — the application thinks it's talking to one MySQL instance, but Vitess transparently routes queries to the correct shard. It was created at YouTube (which runs thousands of MySQL shards through Vitess) and is now a CNCF graduated project. The architecture: VTGate (proxy that accepts MySQL protocol, parses SQL, routes to the right shard based on vindex — Vitess's equivalent of a shard key) + VTTablet (sidecar per MySQL instance managing schema, backups, monitoring). Vitess handles cross-shard transactions (two-phase commit for scattered writes), online schema migrations (change column types without locking the table), and vertical/horizontal sharding splits. Companies like YouTube, Slack, Square, and GitHub (formerly) use Vitess to scale MySQL beyond a single machine without rewriting applications.

### PgBouncer
PgBouncer is a lightweight connection pooler for PostgreSQL — it sits between the application and PostgreSQL, maintaining a small pool of actual database connections (e.g., 20) while accepting thousands of client connections. This is critical because each PostgreSQL connection uses ~10MB of memory (for the backend process), so 1,000 connections = 10GB of RAM consumed just by connection overhead. PgBouncer supports three pooling modes: session pooling (connection assigned for the entire session — least efficient), transaction pooling (connection assigned per transaction — most efficient, the default I use), and statement pooling (per SQL statement — breaks session-level features like temporary tables). The key limitation is that transaction pooling breaks session-level features (SET commands, temporary tables, advisory locks). For MySQL, the equivalent tool is ProxySQL. I always put PgBouncer in front of PostgreSQL in production — it's the single highest-impact performance optimization for connection-heavy applications.

### Istio
Istio is a service mesh built on Envoy proxies — it provides traffic management, security, and observability for microservices without changing application code. Every pod gets a sidecar Envoy proxy that intercepts all inbound and outbound traffic. This enables mTLS (mutual TLS encryption between services automatically — no code changes), intelligent routing (canary deploys with 5% traffic to new version, circuit breaking that stops sending to failing services), and distributed tracing (Envoy automatically injects and propagates trace headers). The control plane (Istiod) configures all the Envoy sidecars dynamically. The trade-off is complexity and overhead — every request now goes through two Envoy proxies (client sidecar → server sidecar), adding ~1-5ms latency, and the Istio control plane itself requires management. I'd use Istio in large microservice deployments (>50 services) where mTLS, fine-grained routing, and observability are worth the complexity. Linkerd is a lighter alternative.

### Amazon CloudFront
CloudFront is AWS's CDN with ~600 edge locations (PoPs) worldwide — it caches static content (images, CSS, JS) and can route dynamic requests to origin servers (ALB, S3, EC2). It integrates natively with AWS services: S3 as origin (with Origin Access Identity for security), Lambda@Edge (run JavaScript at edge locations for auth checks, A/B testing, URL rewriting without hitting origin), and AWS WAF (Web Application Firewall for SQL injection / XSS protection). CloudFront uses TTL-based caching with invalidation (I can invalidate specific paths immediately when content changes). Pricing is based on data transfer out to the internet (cheaper than direct EC2/S3 egress) and request count. I'd choose CloudFront when my infrastructure is AWS-native — the integration with S3, Lambda@Edge, and WAF makes it the path of least resistance. For non-AWS or multi-cloud, Cloudflare is typically simpler and cheaper.

### Akamai
Akamai is the oldest and largest CDN provider (~4,200 edge locations in 130+ countries) — they pioneered the CDN industry in the late 1990s. Akamai is enterprise-grade: extensive SLA guarantees, dedicated support, advanced security (Kona Site Defender for DDoS protection), and edge compute (EdgeWorkers). Apple, Microsoft, and many Fortune 500 companies use Akamai. The trade-off is cost — Akamai is significantly more expensive than CloudFront or Cloudflare, and the management console/API is more complex. I'd choose Akamai when I need the largest physical footprint, enterprise SLAs, or have specific compliance requirements that Akamai certifies. For most startups and mid-size companies, Cloudflare or CloudFront are better value.

### Amazon Aurora
Aurora is AWS's cloud-native MySQL/PostgreSQL-compatible database — it separates compute (the database instances) from storage (a distributed storage volume replicated across 3 AZs). This separation means storage auto-scales (up to 128TB without provisioning), replicas don't need their own copy of data (they share the storage volume), and failover is fast (promoting a replica takes ~10 seconds since no data copying is needed). Aurora provides up to 15 read replicas with sub-10ms replication lag (vs MySQL's typical 100ms+ async replication). Aurora Serverless v2 auto-scales compute capacity based on load (0.5 to 128 ACU — Aurora Capacity Units), ideal for variable workloads. The trade-off is cost (Aurora is 20% more expensive than RDS MySQL/PostgreSQL) and AWS lock-in. I'd choose Aurora for managed MySQL/PostgreSQL when I need fast failover, many read replicas, and auto-scaling storage.

### Apache Hadoop / HDFS
Hadoop is a distributed storage and processing framework — HDFS (Hadoop Distributed File System) stores massive files by splitting them into 128MB blocks distributed across DataNodes (with 3x replication), while MapReduce processes data by sending compute to where the data lives (data locality). The NameNode tracks which blocks live on which DataNodes. Hadoop pioneered the "move compute to data" paradigm — instead of downloading petabytes to a processing server, you run the processing code on the nodes that already have the data blocks. MapReduce works in two phases: Map (filter and transform each record in parallel) and Reduce (aggregate results by key). Today, Hadoop/MapReduce is largely superseded by Spark (100x faster due to in-memory computation) and cloud-native alternatives (S3 for storage, Spark/Flink for compute). HDFS is still used as a data lake storage layer, but modern architectures often use S3 + Parquet instead. Companies like Yahoo (created Hadoop), Facebook, and LinkedIn built their early data infrastructure on Hadoop.

### Presto / Trino
Presto (now Trino after a community fork) is a distributed SQL query engine for running ad-hoc analytics across multiple data sources — it can query data in S3, HDFS, MySQL, PostgreSQL, Kafka, and Cassandra simultaneously using standard SQL, without moving or copying data. It uses a federation architecture: a coordinator parses the SQL, creates an execution plan, and workers scan data from the source systems in parallel. The key insight is that Presto doesn't store data — it's a compute-only engine that pushes down queries to where data already lives. This makes it perfect for interactive analytics on data lakes (querying Parquet files on S3 with ANSI SQL). Facebook created Presto for running SQL queries on their 300PB+ data warehouse. Companies like Uber, Netflix, and Airbnb use Trino for ad-hoc analytics, replacing the old "load data into a warehouse first" model with "query data wherever it lives."

### Snowflake
Snowflake is a cloud-native data warehouse built on a separation of compute and storage — storage is managed on S3/Azure Blob/GCS (pay per GB stored), and compute is provided by virtual warehouses (independent clusters that can be started/stopped/sized independently). This means I can run a heavy analytics query on an XLARGE warehouse, then immediately scale down to XSMALL for a light dashboard — paying only for compute seconds used. Snowflake supports standard SQL, semi-structured data (JSON, Avro, Parquet stored in VARIANT columns), and data sharing (securely share datasets with external companies without copying data). The trade-off vs Spark/Trino is cost — Snowflake charges by the second for compute, and poorly optimized queries can become very expensive. I'd choose Snowflake when I want a fully managed warehouse with no infrastructure management — Capital One, DoorDash, and Adobe use it heavily.

### Amazon Redshift / BigQuery
Redshift is AWS's managed data warehouse based on PostgreSQL (columnar storage, MPP — Massively Parallel Processing with a leader node and compute nodes). It excels at analytical queries on large datasets (TB to PB scale) using columnar storage (reads only needed columns) and zone maps (skip blocks that don't match the filter). BigQuery is Google's serverless alternative — no clusters to manage, pay-per-query pricing ($5 per TB scanned), and it auto-scales to any query size. BigQuery uses Dremel (Google's internal query engine) with a tree architecture (root server → intermediate servers → leaf servers that scan data). I'd choose BigQuery for serverless simplicity and pay-per-query (great for unpredictable workloads), and Redshift when I want more control over compute resources and predictable performance for recurring heavy queries. Both compete with Snowflake — the choice often comes down to cloud provider preference.

### Schema Registry
Schema Registry is a service (Confluent's for Kafka) that stores and validates Protobuf/Avro/JSON schemas for event data — producers register a schema before sending events, consumers fetch the schema to deserialize, and the registry enforces compatibility rules. BACKWARD compatibility means new schema can read old data (adding optional fields — OK). FORWARD compatibility means old schema can read new data (removing fields — OK). FULL compatibility means both. This prevents the #1 bug in event-driven architectures: a producer changes the event format, and all consumers crash because they can't deserialize it. Schema Registry rejects breaking changes (like changing a field type or removing a required field) before the event is produced. Netflix and LinkedIn use Schema Registry with Avro schemas for all Kafka events — ensuring every consumer can safely deserialize every event, even during rolling deployments with different schema versions.

### Apache Avro
Avro is a data serialization system (like Protobuf) used heavily with Kafka — it uses JSON for schema definition (richer types than Protobuf) and binary for data encoding (compact). The key difference from Protobuf: Avro schemas are dynamically resolved at read time (the reader fetches the writer's schema from Schema Registry and resolves differences), while Protobuf relies on generated code at compile time. Avro's schema evolution is more flexible — adding fields is backward compatible as long as the new field has a default value. Avro is the standard serialization format for Kafka in large enterprises because Schema Registry + Avro provides end-to-end schema management. The trade-off vs Protobuf is performance — Avro is slightly slower for serialization and doesn't have native code generation for as many languages.

### Amazon Kinesis / Amazon SNS
Amazon SNS (Simple Notification Service) is a pub/sub messaging service — publishers send messages to topics, and multiple subscribers (SQS queues, Lambda functions, HTTP endpoints, email, SMS) receive copies simultaneously. SNS provides at-least-once delivery and supports message filtering (subscriber only receives messages matching attribute filters) and message deduplication (for FIFO topics). SNS is commonly paired with SQS — the "fanout" pattern: SNS topic fans out to multiple SQS queues, each processed independently by different workers. For example, an order-placed event published to SNS can trigger email confirmation (via SQS → email worker), inventory update (via SQS → inventory service), and analytics ingestion (via SQS → Redshift loader) — all decoupled. SNS is simple and serverless but doesn't offer Kafka's event retention, replay, or ordering guarantees.

### Amazon Lambda (Serverless)
AWS Lambda is a serverless compute service — I upload code (Python, Node.js, Go, Java), and AWS runs it on demand without provisioning servers. I pay per invocation (number of requests × execution duration in milliseconds × memory allocated), and Lambda auto-scales from 0 to thousands of concurrent executions instantly. Common triggers: API Gateway (REST API), S3 events (process uploaded files), DynamoDB Streams (react to data changes), SQS (process queue messages), and EventBridge (scheduled cron-like triggers). The key limitation is the 15-minute execution timeout — Lambda is for short-lived functions, not long-running processes. Cold starts (the delay when a new container is initialized for the first request) add 100-500ms latency for the first invocation after idle time. For latency-sensitive workloads, I use provisioned concurrency (keep N instances warm). Lambda is ideal for event-driven architectures — upload to S3 → Lambda generates thumbnail → Lambda updates database → Lambda sends notification. Companies like Coca-Cola, iRobot, and Nordstrom run significant workloads on Lambda.

### Apache HBase
HBase is a distributed NoSQL database built on top of HDFS — it's Google Bigtable's open-source equivalent, using the same data model (row key, column families, columns) and storage architecture (LSM-tree with HFile storage on HDFS). HBase provides strong consistency per row (unlike Cassandra's tunable consistency) and is optimized for read-heavy workloads on massive datasets. It uses ZooKeeper for coordination and HDFS for storage (so data is replicated 3x by HDFS). HBase is commonly used in Hadoop ecosystem deployments for real-time read/write access to big data — Facebook used HBase for their Messenger backend (before moving to custom solutions). Today, HBase is largely superseded by Cassandra (which is simpler to operate, peer-to-peer, multi-DC) and Cloud Bigtable (managed). I'd choose HBase only if I'm already invested in the Hadoop ecosystem.

### ScyllaDB
ScyllaDB is a C++ rewrite of Cassandra — it's wire-compatible with Cassandra (uses CQL, same data model) but written in C++ instead of Java, using a thread-per-core architecture (Seastar framework) instead of JVM threads. This gives it 5-10x better performance than Cassandra on the same hardware — lower latency, higher throughput, and no JVM garbage collection pauses. ScyllaDB achieves this through "sharding per core" — each CPU core independently handles a subset of data and requests, with no cross-core locking. Discord moved from Cassandra to ScyllaDB for their message storage (billions of messages) because Cassandra's JVM GC pauses caused latency spikes. The trade-off is a smaller community than Cassandra and some Cassandra-compatible features being work-in-progress. I'd choose ScyllaDB when I need Cassandra's data model but with better latency consistency and no GC pauses.

### CockroachDB
CockroachDB is a distributed SQL database that provides ACID transactions across regions without manual sharding — it's designed to be a "Spanner for everyone" (open-source, PostgreSQL-compatible). It uses Raft consensus for replicating data across nodes, and automatically ranges (splits tables into ranges that are each a Raft group) and rebalances data. Reads and writes go through the range leaseholder, which coordinates with Raft replicas for consistency. The key value is global ACID: I can write in Mumbai and read in New York with strong consistency. The trade-off is latency — cross-region writes take 100-200ms (Paxos/Raft round-trip between continents), and the system adds overhead vs a single PostgreSQL instance. I'd choose CockroachDB when I need global ACID transactions but can't use Google Spanner (because it's GCP-only or too expensive) — Netflix, DoorDash, and DoorDash use it.

### Amazon CloudWatch
CloudWatch is AWS's built-in monitoring and observability service — it collects metrics (CPU, memory, network, custom application metrics via the PutMetricData API), logs (via CloudWatch Logs from Lambda, ECS, EC2, and application SDKs), and traces (via AWS X-Ray integration). CloudWatch Alarms trigger when metrics cross thresholds (e.g., "CPU > 80% for 5 minutes" → trigger auto-scaling or SNS notification). It's the default monitoring for any AWS infrastructure — Lambda automatically sends metrics, EC2 sends system metrics, and RDS sends database metrics. The trade-off is that CloudWatch is AWS-specific and less flexible than Prometheus + Grafana — but for AWS-native deployments, it requires zero setup. I typically use CloudWatch for infrastructure metrics (is the server alive?) and Prometheus + Grafana for application metrics (what's my p99 latency by endpoint?).

### OpenTelemetry
OpenTelemetry is a vendor-neutral observability standard (CNCF) that unifies metrics, logs, and traces into a single instrumentation API — instead of installing Datadog's SDK for metrics + Jaeger's SDK for traces + Fluentd for logs, I install one OpenTelemetry SDK and configure the export destination (Jaeger, Prometheus, Datadog, Zipkin, Honeycomb). The SDK auto-instruments HTTP, gRPC, database calls, and message queue operations — automatically generating trace spans with minimal code changes. Context propagation ensures a trace ID started at the API gateway flows through every downstream service via headers. OpenTelemetry is replacing vendor-specific instrumentation (Zipkin's Brave, Jaeger's client, Datadog's dd-trace) — companies are standardizing on OTLP (OpenTelemetry Protocol) to avoid vendor lock-in for observability. I always recommend OpenTelemetry for new projects — instrument once, switch backends without rewriting code.

### TensorFlow / PyTorch
TensorFlow (Google) and PyTorch (Meta/Facebook) are the two dominant deep learning frameworks. PyTorch uses a dynamic computational graph (define-by-run) — I write standard Python, and the graph is built as the code executes, making debugging intuitive (use print statements, standard Python debugger). This made PyTorch the dominant choice in research (90%+ of new research papers use PyTorch). TensorFlow 2.x uses Keras as its high-level API and supports eager execution (dynamic graphs), but its heritage is static graphs (define-then-run) — compile the graph first, then execute, which enables optimizations like XLA (Accelerated Linear Algebra) but is harder to debug. TensorFlow has better production deployment tooling (TF Serving, TensorFlow Lite for mobile, TensorFlow.js for browser). The industry trend is clear: PyTorch for research and experimentation, with TorchServe or ONNX export for production. Google products (Search, Photos, Translate) use TensorFlow/JAX internally; Meta (News Feed, content moderation, AR effects) uses PyTorch exclusively.

### Long Polling
Long polling is a legacy technique for real-time updates where the client sends an HTTP request and the server holds it open (doesn't respond immediately) until new data is available or a timeout occurs — then the client immediately sends another request. It was the standard for real-time before WebSocket became universal (Facebook Chat and early Gmail Chat used long polling). The advantage is it works over standard HTTP (no protocol upgrade, no proxy issues), but the disadvantages are significant: HTTP header overhead per request (~800 bytes), latency between when data is available and when the client re-requests (polling gap), and connection churn. I'd only use long polling today as a fallback when WebSocket is blocked (e.g., strict corporate proxy) — it's strictly worse than WebSocket and SSE for new applications.

### QUIC / HTTP/3
QUIC is a transport protocol built on UDP (not TCP) — created by Google and now the foundation of HTTP/3. It solves TCP's head-of-line blocking: in HTTP/2 over TCP, if one packet is lost, ALL streams on that connection stall until the packet is retransmitted. QUIC implements streams natively at the transport layer (over UDP), so if one stream loses a packet, only that stream stalls — others continue. QUIC also eliminates the TCP + TLS handshake delay: the first connection combines transport and cryptographic handshake (1-RTT), and returning connections use 0-RTT (resume immediately with cached keys). Connection Migration: QUIC connections are identified by a connection ID, not source IP — so switching from WiFi to cellular doesn't drop the connection (impossible with TCP). Companies like Google (all Google services), Cloudflare, and Facebook use QUIC/HTTP/3 for significant traffic. The protocol is still gaining adoption but is the clear future of web transport.

### XML/Binary communication
XMPP (Extensible Messaging and Presence Protocol) is an XML-based protocol originally created for instant messaging (Jabber, Google Talk) — it uses a federated client-server model where anyone can run a server and users on different servers can communicate (like email). WhatsApp originally used a customized version of XMPP for their messaging backend before moving to a custom protocol. XMPP uses three stanza types: message (chat messages), presence (online/offline status), and IQ (info/query for service discovery and configuration). The XML format is verbose (lots of tags), making it inefficient for mobile devices with limited bandwidth — which is why WhatsApp moved away from it. Today, XMPP is still used in enterprise chat (Cisco Jabber, some HIPAA-compliant systems) but has largely been replaced by WebSocket-based custom protocols with binary (Protobuf/Thrift) encoding.

### Celery
Celery is a Python task queue library — I define tasks as regular Python functions decorated with @app.task, and instead of calling them directly, I use task.delay(args) which serializes the arguments and pushes them to a broker (Redis or RabbitMQ). Worker processes pick up tasks from the broker, execute them, and store results in a result backend (Redis or database). Celery supports task retries with exponential backoff, task chaining (task A → task B → task C), task groups (run N tasks in parallel), rate limiting (max 100 tasks/min per worker), and scheduled tasks via Celery Beat (cron-like scheduling). It's the standard async task solution for Python/Django/Flask applications — I use it for sending emails, processing images, generating reports, and any operation that takes >200ms and shouldn't block the HTTP response. The trade-off is that Celery is Python-specific (not cross-language like SQS or Kafka) and the worker management requires operational overhead (monitoring, scaling, handling stuck tasks).

### NATS
NATS is a lightweight, high-performance messaging system designed for microservices and cloud-native applications — it's simpler than Kafka (no persistence by default, no partitions, no consumer groups) and much faster (sub-millisecond latency, millions of messages per second on a single server). It uses a simple subject-based routing model: publishers send to subjects like "orders.created" and subscribers listen with wildcards like "orders.*" or "orders.>" (recursive wildcard). JetStream (NATS's persistence layer) adds Kafka-like durability with streams, consumers, and exactly-once delivery. Leaf nodes enable edge messaging (run a local NATS server that connects to a central cluster). I'd choose NATS when I need ultra-low-latency messaging with simple deployment — it's popular in IoT, financial trading systems, and microservice backends. The trade-off vs Kafka is no built-in event streaming analytics ecosystem (no Kafka Connect, no native ksqlDB equivalent).

### Apache Storm / Apache Samza
Storm is a real-time stream processing framework (created by Twitter) — it processes data in tuples (named values) flowing through spouts (data sources) and bolts (processing units) arranged in a topology (DAG). Storm was the first popular stream processing system but has largely been replaced by Flink (which provides exactly-once guarantees and better state management) and Spark Structured Streaming. Samza is LinkedIn's stream processing framework built on Kafka — it uses Kafka for both input and output, with local RocksDB for state storage (stateful processing without external database). Samza is tightly integrated with Kafka and was LinkedIn's standard for real-time processing before they moved to Flink. Today, for stream processing, I'd choose Flink (best-in-class for exactly-once, stateful processing) or Spark Structured Streaming (if already using Spark for batch). Storm and Samza are primarily relevant for understanding existing systems at Twitter and LinkedIn respectively.
